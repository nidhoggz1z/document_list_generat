日期：2026-10-22（Asia/Shanghai）。状态：待用户确认。

已有 [接口文档](./接口文档.md) 和 OpenAPI 是接口草案；其中尚未明确确认的业务选择、必填要求、容量及超时参数，不视为需求冻结。本轮不修改业务代码，也不按以下假设直接开始实现。确认后再起草正式 spec 并同步接口草案。

## 已确认事项

| 编号 | 已确认内容 |
| --- | --- |
| C01 | 输入包含一个文件 URL 和用户给定结构的业务 JSON。 |
| C02 | 从 URL 文件内容中通过大模型提取产品等信息，再检索对应规则清单。 |
| C03 | 业务 JSON、URL 提取内容、规则清单内容共同输入生成模型，输出个性化规则清单 JSON。 |
| C04 | 每条至少包括放款材料、来源系统、制度依据、发布日期、发布部门；字段查不到时保留字段，值为 `""`。 |
| C05 | 采用同步接口，一次请求获取完整 JSON。示例中的 60 条不是固定数量。 |
| C06 | 两个大模型节点通过 API Key 调用，部署到其他机器时替换配置。实际密钥在部署环境设置，无需在澄清中提供。 |
| C07 | 整体 `status` 为 `SUCCESS` 或 `NEEDS_REVIEW`，条目适用性为 `APPLICABLE`、`NOT_APPLICABLE`、`NEEDS_CONFIRMATION`，由服务端计算。仅缺展示字段不单独触发人工确认状态。 |

还有一个status的问题要和你沟通一下，现在的两个status不满足要求，下游接口要求的是下面这几个
①　进行中——AI任务正在处理中，暂未返回处理结果；
②　已完成——AI任务处理完成，已返回放款材料清单结果；
③　待处理——AI任务正在排队等待处理；
④　失败——AI任务异常，放款材料清单任务处理失败；
⑤　终止——AI任务终止，放款材料清单任务终止。
具体参数名为：
 PROCESSING("PROCESSING", "处理中", "进行中"),
    PENDING("PENDING", "待处理", "任务正在排队等待处理"),
    DONE("DONE", "处理完成", "已完成"),
    FAILED("FAILED", "处理失败", "任务处理失败"),
    TERMINATED("TERMINATED", "终止", "任务终止");

同时我和前端沟通后决定整个项目逻辑也需要调整，我们不需要主动传输，而是上游发来创建任务的JSON后，先返回一个响应JSON，之后等待上游查询，生成出的内容存储在本地，同一个业务编号下可能会有多个任务编号，查询时会通过业务编号和任务编号进行查询，如果已经生成完成则返回内容。注意，有可能会出现同一个业务编号下，有多个任务进行处理，这部分的逻辑是，有一个新的任务进来，如果之前的处理完了，就按之前的逻辑保存，如果没有处理完，则直接中断任务，直接执行最新的。而对于不同业务编号的任务，则排队正常处理。
