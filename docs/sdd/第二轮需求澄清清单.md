# 第二轮需求澄清清单

日期：2026-10-22（Asia/Shanghai）。状态：待用户答复。

依据：[用户已填写的第一轮清单](./需求澄清与假设清单.md)，包括文末的新建任务、状态查询及串行调度要求；已查看其中引用的批复截图。本文件保留原答复，不恢复已删除的假设清单，不修改原接口文档或 OpenAPI。以下选择均未自动定稿。

## 本轮已明确的需求变化

- 从同步生成改为创建任务后先响应，再由上游主动查询；服务不主动推送结果。
- 新建任务接收扁平业务 JSON，新增 `bsnEvtId`，创建成功响应包含 `bsnEvtId`、`userNo`、`taskId`、`autoReply="task created"`。
- 查询 JSON 包含 `bsnEvtId`、`userNo`、`taskId`；按业务编号与任务编号定位记录，历史任务及结果保存在本地。
- 状态使用 `PROCESSING`、`PENDING`、`DONE`、`FAILED`、`TERMINATED`，替代原先整体结果状态。非完成状态按用户给定的四字段响应返回；完成状态还要返回生成清单。
- 全局任务串行处理；不同业务编号排队。同一业务新任务替换未完成旧任务，已完成的旧结果保留。
- 文件为批复，首期支持文本 PDF、扫描 PDF；提取全文和相关事实；不跟随文档里的附件和链接。
- 处理批复中的全部产品，使用各产品对应的当前清单全部规则。产品无法识别、清单不存在或处理中间结果不完整时整次失败，不回退 JSON 产品。
- 相同事实冲突时以批复提取内容为准。不使用业务代码字典。
- 只返回需要提交且适用的材料；待确认规则按适用处理；不返回核查事项、不适用项和排除理由。
- 材料按实际担保人等对象个性化展开，不合并不同对象的同名材料。只筛选和细化要求，不任意新增材料。
- 每条五个展示字段查不到时置空；无已明确要求的附加条目字段。
- 文件体积不超过用户描述的 10m，负载不超过 5 个的量级；暂不确定超时指标。本轮不继续要求部署、权限或脱敏方案；代码实现范围后续放入 src 以适配打包。

## 待确认问题

### R01：批复 PDF 地址从哪里获取？

新版创建 JSON 没有 `fileUrl`，只有 `replyImageUrl`；第一轮 Q03 又明确只读取 fileUrl。Q16 中“影响地址和押品类型是获取不到的”，“影响地址”是否指批复影像地址？

批复文件是直接上传的，也就是创建任务时你会收到两个：1，前端传来的JSON。2，前端上传的文件。

### R02：正在执行的同业务任务被替换后，新任务是否插队？

例：A1 正在执行，B1、C1 正在排队，此时 A2 到来。

- 使用方案二：A1 终止，先执行已排队的 B1、C1，再执行 A2。



### R03：排队中的同业务任务被替换时，队列位置如何处理？

例：A1 执行中，队列为 B1、C1，此时 B2 到来。

- 采用这个方案：B2 重新排到队尾：A1 → C1 → B2。

无论选哪个，B2 都不打断不同业务的 A1；这一理解正确

### R04：同业务已有多个未完成任务时，是否全部终止？

若 A1 正在执行、A2 尚待处理，A3 又到来，将 A1、A2 都置为 TERMINATED，只保留 A3，已 DONE/FAILED/TERMINATED 的历史记录均不改变

### R05：没有模型取消接口时，“中断”和“串行”以什么为准？

如果旧任务已发出模型请求，而模型服务不支持真正取消推理：

- 关闭本地请求、将旧任务置为 TERMINATED、不接收旧结果，立即执行新任务；模型服务端的旧推理可能尚未结束。

### R06：TERMINATED 是否还包括人工主动终止？

本期只实现“同业务新任务替换旧任务”触发终止。被新任务替换的旧任务，即使随后收到模型成功响应，也应保持 TERMINATED 且不发布该结果

### R07：相同业务编号＋相同任务编号重复创建，历史如何保存和查询？

第一轮已明确相同输入重复生成。若重复创建的 `bsnEvtId + taskId` 完全相同，是覆盖该任务原记录，相同键但业务内容发生变化也允许重新执行？

### R08：程序重启后，未完成任务如何恢复？

历史状态与结果会持久化；重启时原 PENDING/PROCESSING 任务的策略：全部未完成任务置为失败/终止？

### R10：失败原因是否需要给下游展示？

你提供的非完成响应只有四个字段。FAILED 加一行reason，输出失败原因，响应字段格式如下

  {

"bsnEvtId":"", //业务编码

  "userNo": "",       // 用户编号

  "taskId": "",       // 任务编号

  "status": "",       // 任务状态

  "reason": "",       // 失败原因

}

### R11：不存在的任务及无效请求如何响应？

查询的 `bsnEvtId + taskId` 不存在时，用JSON字段回复  

{

"reply":"任务未创建", //业务编码

}

### R12：批复中“全部产品”具体按哪列、哪种粒度确定？

两列不同时，按“可售产品”匹配清单，同一产品在多条授信记录出现、金额或条件不同，是只查一次并汇总条件

### R13：多产品的同名材料如何统一返回？

不同产品的清单可能都有借款人营业执照等共性材料。跨产品也不合并、分别保留吗？如果每条只允许五个字段，是否在 materialName 中加入产品名，以区分相同材料所属产品；还是不展示产品归属？

### R14：只有五个展示字段时，“补充具体要求”写在哪里？

例如原项是租赁合同，批复要求收取特定项目合同及附属材料。将具体要求写入 materialName，例如“某项目租赁合同（含批复要求的附件）”

### R15：来源系统、发布日期和发布部门的业务含义是什么？

这些东西你直接从对应的材料文档里查，如果查不到，现在默认，来源系统填：上银办；发布日期填：2026年。发布部门填：上海银行

### R16：“排除项”具体指什么？

Q11 提到“只要不是排除项内容均可直接采用”。这里是指只要不是筛选后确认不适用的材料，就直接采用。

### R17：押品类型“取不到”与空字段“代表没有”如何区分？

Q16 明确 cltlTp 获取不到，Q18 又明确空值代表没有。若已知存在抵押或押品，但类型为空，按“有押品、类型未知”处理，批复也没写清时，将相关可能适用的材料都按适用输出？

### R18：批复未提及某事实时，能否使用 JSON 补充？

以批复为准的冲突优先级已明确。还需确认“未提及”是否区别于“明确没有”：例如批复没有列出担保人姓名，但 JSON 有 A、B，使用 JSON 展开材料；批复明确无担保、JSON 有担保人时使用 JSON

### R19：新版创建与查询 JSON 哪些字段必须非空？

仅 bsnEvtId、userNo、taskId 及有效批复地址必填，其余字段包括 contractNum/subcontractNum 均可空或缺失，可选字段传 null 时忽略已明确；必要标识或批复地址为 null 时可以创建？

### R20：模型 API 协议与内部调用次数还需做两项明确选择

第一轮 Q20 的“API 接口”意思是将使用APIkey的形式提供大模型服务，Q21 允许分批和有限重试。
